# SDD 文件管理與執行規範（docs/AGENTS.md）

> **適用範圍**：本文件適用於 `docs/` 與其所有子目錄，是 Spec、Plan、ADR 的**格式、命名、生命週期、來源驗證及 SDD 流程唯一制度正本**。
>
> **使用方式**：Codex 修改專案程式碼時，須由根目錄 `AGENTS.md` 提醒讀取本規範；`docs/AGENTS.md` 的作用範圍不會自動涵蓋 `docs/` 以外的程式碼。
>
> **建檔原則**：不預先建立空白 Spec、Plan、ADR 或索引；`docs/templates/` 中的三份模板是固定格式來源，隨本規範一同維護。正式工作文件仍只在需要時建立。本文中的檔名、ID 和內容僅為格式範例，並不代表相關檔案、功能或決策已存在或已核准。

## 1. 目標、適用規範與文件分工

1. 採 **Spec-anchored SDD（規格錨定的規格驅動開發）**：先明確定義預期行為和驗收條件，再擬定實作計畫、拆分任務、實作及驗證；功能完成後持續維護規格。
2. 根目錄 `AGENTS.md` 管理專案整體開發、框架、程式碼和 SDD 入口；本文件專門管理 `docs/` 文件制度。不同規範同時適用時應一併遵守；涉及已核准內容的衝突須先回報，不能自行選擇忽略。
3. **Spec** 記錄需求、範圍、可觀察行為、業務規則、非功能要求與驗收標準，回答「要達成什麼」。
4. **Plan** 記錄技術方案、影響範圍、任務、驗證、執行歷程與交付結果，回答「如何完成、實際做了什麼」；**Design 與 Tasks 是 Plan 的內容，不是另外的文件類型**。
5. **ADR** 記錄具長期影響的架構／技術決策、替代方案、理由與影響；只有必要時建立，不要求每個 Spec 或 Plan 都有 ADR。
6. **唯一正本**：需求以對應 Spec 為正本、技術計畫和任務進度以 Plan 為正本、架構決策以 ADR 為正本、本制度以 `docs/AGENTS.md` 為正本。其他地方只能摘要並使用 ID 與相對路徑引用，不複製整段維護。
7. **真實現況與目標行為分開**：程式碼及可重現測試是「目前如何運作」的證據；已核准 Spec 是「應如何運作」的依據。衝突時列出差異、影響與選項，停止受影響部分，取得確認後再變更。
8. 本專案文件原則使用繁體中文；程式識別字、API、檔名、狀態值、技術術語依實際英文原名撰寫。

## 2. 目錄結構、命名與識別碼

```text
project/
├── AGENTS.md                       # 專案開發規範及 SDD 入口
└── docs/
    ├── AGENTS.md                   # 本文件，唯一制度正本
    ├── index.md                    # 首次有正式文件時才建立
    ├── specs/
    │   └── YYYYMMDD-NNNN-topic.md  # 按需建立
    ├── plans/
    │   └── YYYYMMDD-NNNN-topic.md  # 按需建立；完成後不搬移
    ├── adr/
    │   └── YYYYMMDD-NNNN-topic.md  # 按需建立
    └── templates/
        ├── spec.md               # Spec 的固定格式模板
        ├── plan.md               # Plan 的固定格式模板
        └── adr.md                # ADR 的固定格式模板
```

1. **正式檔名**：`YYYYMMDD-NNNN-topic-name.md`，日期為首次建檔的本地日期，`NNNN` 為至少四位數流水號，主題為小寫英文 kebab-case。
2. **正式文件 ID**：`SPEC-YYYYMMDD-NNNN`、`PLAN-YYYYMMDD-NNNN`、`ADR-YYYYMMDD-NNNN`。`SPEC`、`PLAN`、`ADR` 為本專案採用的文件識別慣例，不宣稱是全業界唯一標準。
3. **流水號作用域**：依「文件類型 + 首次建立日期」各自從 `0001` 遞增；同類型、同日期不得重複。不同類型或日期可存在相同流水號。
4. **不可重新使用**：ID 與首次建檔日期建立後不可更改；改主題檔名、修訂、完成、取消或被取代都不得重編或回收。新建前檢查目錄、索引以及可用的 Git 歷史；多人合併前再檢查衝突。
5. **編號不代表關係**：同日期、同編號的 Spec 和 Plan 不會自動關聯；關係一律由 Metadata 的 `related_*` ID 與正文相對連結表達。
6. **不在檔名加狀態或版本**：不得使用 `final`、`new`、`v2`、`approved` 等字樣區分版本。
7. **一份跨多子專案文件**：`project` 為主要負責子專案，其他列入 `related_projects`；不要為每個子專案複製正本。
8. **索引**：首次建立正式文件時按需建立 `docs/index.md`；只記錄文件 ID、標題、類型、狀態、主要子專案、相對連結及主要關聯。新增、改名、狀態或關聯變更時更新；不要在索引重複完整規格。
9. **舊檔遷移**：原有不同命名制度的文件不能自動批次改名。先列出舊／新 ID、路徑與引用影響，取得授權後才遷移。

**格式示例（不是既有檔案）**：

| 類型 | 路徑 | 文件 ID |
| --- | --- | --- |
| Spec | `docs/specs/20261018-0001-member-login.md` | `SPEC-20261018-0001` |
| Plan | `docs/plans/20261018-0001-member-login.md` | `PLAN-20261018-0001` |
| ADR | `docs/adr/20261018-0001-authentication-policy.md` | `ADR-20261018-0001` |

### 模板建立與維護規則

1. `docs/templates/spec.md`、`docs/templates/plan.md`、`docs/templates/adr.md` 是**模板檔案**，不屬於正式 Spec、Plan、ADR；不分配文件 ID、不進入文件索引，也不參與生命週期。
2. Codex 建立正式文件前，必須先讀取本 `AGENTS.md` 及相應模板，以模板複製建立新檔，再依實際任務填寫；不得自行發明 Metadata、章節名稱、順序或追溯欄位。
3. 模板內的 `YYYYMMDD`、`NNNN`、標題、`待填`、示範 ID 等均為佔位內容；產出正式文件時必須替換為經查證的資訊，未知事項按第 5 節標示「待確認」，不適用則寫原因。
4. 模板的 Metadata、章節標題、必要記錄欄位必須符合本規範第 3、6～8 節；若模板與本規範矛盾，停止相關建立／修改工作，先修正一致後再產生正式文件。
5. 修改固定格式時須**同一次變更**更新本規範及受影響模板，並核對相同章節順序、Metadata 及 ID 引用方式；不得只改其中一處。
6. 正式文件內容的唯一正本仍是該 Spec／Plan／ADR；模板僅規定如何撰寫，不能用來保存真實需求、測試結果或決策。

## 3. 統一 Metadata 與欄位規則

所有正式 Spec、Plan、ADR 必須使用**完全相同的 YAML Front Matter 欄位集合和順序**；依文件類型填入不同值。未有關聯時用 `[]`，單一取代指標沒有值時用 `null`，不得省略欄位。

```yaml
---
id: SPEC-20261018-0001
type: spec
title: 會員登入功能規格
project: store
status: draft
created: 2026-10-18
updated: 2026-10-18
related_projects: []
related_specs: []
related_plans: []
related_adrs: []
supersedes: []
superseded_by: null
---
```

| 欄位 | 型別 | 規則 |
| --- | --- | --- |
| `id` | 字串 | 必須與類型、檔名日期及流水號一致，建立後永久不變 |
| `type` | `spec`／`plan`／`adr` | 只允許三種正式文件類型 |
| `title` | 字串 | 清楚描述功能、計畫或決策 |
| `project` | 字串 | 主要負責子專案；未確立代號時用 `root`，不得虛構代號 |
| `status` | 字串 | 僅能使用第 4 節定義的對應類型狀態 |
| `created` | `YYYY-MM-DD` | 首次建立日期，與 ID 日期部分一致 |
| `updated` | `YYYY-MM-DD` | 實質內容或狀態變更時更新 |
| `related_projects` | 字串陣列 | 其他受影響子專案 |
| `related_specs` | ID 陣列 | 現存相關 Spec ID |
| `related_plans` | ID 陣列 | 現存相關 Plan ID |
| `related_adrs` | ID 陣列 | 現存相關 ADR ID |
| `supersedes` | ID 陣列 | 本文件正式取代的同類型舊文件 |
| `superseded_by` | ID 或 `null` | 正式取代本文件的同類型新文件 |

- 三類文件均保留全部欄位，即使該類型通常不使用其中某些關聯。
- `related_*`、`supersedes` 存**文件 ID**；正文「相關文件」使用可開啟的相對 Markdown 路徑。不能將假設中的未建檔文件寫成已存在的 ID。
- 修改 `related_*` 時確認相關正本是否也需要更新反向關聯；`supersedes`／`superseded_by` 必須互相一致。
- Metadata 不用來存整份需求、執行日誌或測試輸出；詳細內容留在固定章節。
- 重要核准需在該文件的變更／決策紀錄留下日期、確認內容及可查證的確認來源；未知核准人或日期不可編造。

## 4. 文件狀態、轉換與審核權限

| 類型 | 正常流程 | 其他狀態 |
| --- | --- | --- |
| Spec | `draft → approved → implemented` | `superseded` |
| Plan | `draft → approved → implementing → completed` | `cancelled` |
| ADR | `proposed → accepted` | `rejected`、`superseded` |

1. `draft`／`proposed` 僅代表提案；Spec `approved`、Plan `approved`、ADR `accepted` 必須由使用者或授權決策者明確確認，Codex 不得自行宣告核准。
2. Spec `implemented` 須所有適用 AC 已驗收通過、必要測試證據完整；Plan `completed` 須 Tasks 和執行／驗證紀錄完整，並註明未解問題與交付結果。
3. 同一 Spec 可以由多個 Plan 實作；單一 Plan 完成不等於整份 Spec 已實現。
4. Plan 進入 `implementing` 必須已實際開始開發。只有規劃討論時不得提前變更狀態。
5. `rejected`、`cancelled`、`superseded` 必須保留原因及日期；已被取代文件不移動、不刪除，並留下雙向追溯。
6. 已 `accepted` 的 ADR 不覆寫決策內容；改變長期決策時建立新 ADR 取代舊 ADR。已 `approved` Spec 的實質需求變更需先提出差異和影響，經確認後修訂或建立替代 Spec。
7. 狀態退回或重啟必須明確記錄原因、原狀態、新狀態及確認來源；不得悄悄將完成文件改寫成草案。
8. Git Commit、程式碼已修改、建置成功或執行測試指令，均不單獨構成需求驗收。

## 5. 文件撰寫的共同強制規範

1. **固定格式**：每種文件都必須依 `docs/templates/` 中對應模板，以及第 6～8 節指定的**完整章節名稱、編號和順序**；不得擅自刪除、合併、改名或調換。
2. **每章都有實質內容**：尚未知的事項寫「待確認」及需要確認的問題；確實不適用時寫「不適用」及原因；不得使用空章節、無意義套話、捏造資訊填滿模板。
3. **詳細程度以可審核／可執行為準**：需求能判斷對錯、技術計畫能逐步執行、Tasks 能各自驗證、決策能看出替代方案與取捨。
4. **章節內允許子標題、表格與必要程式碼**，但不可改變固定的一級文件標題及二級正式章節。
5. 每個文件章節開頭使用一致的來源標記約定簡述（見第 10 節）；涉及專案現況、重要結論與測試結果應標註依據，不必為每句一般敘述添加標記。
6. 原始計畫與後來實際結果分開保存；不得為了讓紀錄看起來吻合而事後改寫原計畫。
7. 提案、決定、推論、已執行驗證和未執行事項必須明確區分；禁止將預計成果寫成實際成果。
8. 同一資料只維護一份正本；其他文件引用其 ID、路徑及必要段落，不貼上大篇副本。

## 6. Spec：固定 12 章與需求規則

Spec 的 `type: spec`、預設 `status: draft`，使用第 3 節共同 Front Matter；**建立時使用 `docs/templates/spec.md`**。正文固定如下：

```markdown
# 功能規格標題

## 1. 文件概述
## 2. 目標與成功標準
## 3. 功能範圍
## 4. 使用者角色與情境
## 5. 功能需求
## 6. 業務規則與限制
## 7. 非功能需求
## 8. 驗收條件
## 9. 相依關係
## 10. 風險與待確認事項
## 11. 需求追溯矩陣
## 12. 規格變更紀錄
```

各章節的**必填資訊**：

| 章節 | 必填內容 |
| --- | --- |
| 1 | 需求背景、問題、來源、適用對象、文件目的 |
| 2 | 可衡量目標、成功標準與邊界 |
| 3 | In Scope、Out of Scope、主要功能與受影響系統 |
| 4 | 角色權限、User Story、主要／例外流程 |
| 5 | 有唯一編號的功能需求、觸發條件、預期行為與優先度（如已確認） |
| 6 | 業務約束、狀態轉換、例外、驗證與資料規則 |
| 7 | 效能、安全性、可用性、可及性及其他適用要求，無則說明理由 |
| 8 | 每個 AC 的前提、操作、可觀察預期結果、對應 REQ |
| 9 | 已知相依、外部介面、相關 Spec／Plan／ADR 的實際連結 |
| 10 | 需求風險、假設、待決問題及其影響 |
| 11 | REQ → AC 對照，確保每條需驗收需求有可檢查標準 |
| 12 | 日期、修改內容、原因、影響、核准狀態及確認來源 |

- 使用 User Story：`作為〈角色〉，我希望〈能力〉，以便〈價值〉`。
- 可驗證行為**優先**使用 EARS 表達，例如 `WHEN 〈觸發條件〉 THEN 系統 SHALL 〈可觀察結果〉`；狀態型、例外型需求按情境採適當句式，不強迫每句都用相同句型。
- 每份 Spec 內使用唯一 `REQ-01`、`REQ-02`……及 `AC-01`、`AC-02`……；跨文件使用完整限定識別，如 `SPEC-20261018-0001#REQ-01`。
- 不在 Spec 記錄逐步程式修改、開發 Task 或測試執行日誌；它們應記在 Plan。

## 7. Plan：固定 14 章與任務規則

Plan 的 `type: plan`、預設 `status: draft`，使用第 3 節共同 Front Matter。技術設計與 Tasks 都是 Plan 的章節，不建立獨立 Design 文件；**建立時使用 `docs/templates/plan.md`**。正文固定如下：

```markdown
# 開發計畫標題

## 1. 計畫概述
## 2. 需求與驗收對照
## 3. 現況與技術限制
## 4. 技術實作方案
## 5. 影響範圍與異動清單
## 6. 工作項目與執行順序
## 7. 測試與驗證計畫
## 8. 風險與應對措施
## 9. 待確認事項
## 10. 計畫變更紀錄
## 11. 實作執行紀錄
## 12. 驗證結果
## 13. 差異與問題紀錄
## 14. 完成與交付摘要
```

各章節的**必填資訊**：

| 章節 | 必填內容 |
| --- | --- |
| 1 | 任務目標、對應 Spec、交付項目、適用範圍 |
| 2 | 本 Plan 處理的 REQ／AC；L2 無 Spec 時列已確認需求來源與可驗收基準 |
| 3 | 實際查得的程式碼、框架版本、資料流、API、限制及其查證依據 |
| 4 | 技術選擇、資料模型、流程、介面、錯誤處理、替代方案與取捨 |
| 5 | 預計新增／修改／刪除的模組、檔案、型別、API／資料契約與相容性 |
| 6 | TASK ID、內容、對應 REQ／AC、相依、執行順序、完成條件與狀態 |
| 7 | TEST ID、對應 AC／TASK、步驟或指令、預期結果及必要環境 |
| 8 | 風險、可能影響、緩解與回退措施 |
| 9 | 技術與資源待決問題、影響、負責確認者（若已知） |
| 10 | **原始核准計畫保留**；另記每次變更日期、原因、影響與核准情況 |
| 11 | 各 TASK 的實際操作、日期、進度、結果、相關程式碼與阻礙 |
| 12 | 各 TEST 的實際執行日期、環境、結果、證據與未執行原因 |
| 13 | 計畫／實作差異、異常、原因、修正方式與遺留問題 |
| 14 | 已完成交付、未完成／未驗證項、相關文件同步情況及交付結論 |

- Plan 內使用唯一 `TASK-01`、`TASK-02`……、`TEST-01`、`TEST-02`……。Task 狀態限定 `pending`、`in_progress`、`done`、`blocked`；Test 狀態限定 `not_run`、`passed`、`failed`、`blocked`。
- 每個 TASK 至少有：工作內容、依賴、對應完整 REQ／AC ID（有 Spec 時）、完成條件、實際驗證方式與狀態。完成條件不得只寫「已寫好」。
- 每個 TEST 至少有：對應需求／任務、指令或步驟、預期結果；執行後補環境、日期、實際輸出摘要、證據和結果。**沒跑過只能記 `not_run`**。
- 追溯鏈為 `REQ → AC → TASK → TEST`；若多個項目互相對應，用表格表示全部關聯，不因一對多而省略。
- 同一 Plan 可以分次實作；第 10 章必須能區分**原定計畫**與**已核准的後續變更**，第 11～14 章記錄實際事實。
- 不能推定預計修改檔案已存在；須先驗證。不能為符合計畫而改寫已核准 Spec。

## 8. ADR：固定 11 章與決策規則

ADR 的 `type: adr`、預設 `status: proposed`，使用第 3 節共同 Front Matter；**建立時使用 `docs/templates/adr.md`**。正文固定如下：

```markdown
# 架構決策標題
```

## 9. SDD 任務分級與標準工作流程

每次任務都依相同階段順序處理；文件產出深度由等級決定。開始前需說明判級及理由，符合多個條件時取較高等級，使用者可以調整等級但不得繞過必要的安全與核准要求。

| 等級 | 觸發條件 | 文件與核准要求 |
| --- | --- | --- |
| **L1** | 修改最多 3 個檔案，且無 Migration、公開契約變更、跨模組或重大架構／業務影響 | 讀取相關現況 → 直接實作 → 驗證；不強制新增 Spec／Plan，但不能違反已核准規格 |
| **L2** | 超過 3 個檔案，或有 Migration、API 等公開契約變更，但未達 L3 | 建立／更新 Plan → 核准 Plan → 實作／驗證；如新增或修改重要業務需求，先建立／更新並核准 Spec |
| **L3** | 跨模組垂直切片、完整重大功能、核心架構或重大業務流程 | 核准 Spec → 核准 Plan → 必要時核准 ADR → 依 TASK 實作 → 雙面向 Review → 驗收與文件同步 |

**標準階段（依順序執行）**：

1. **任務判級與查證**：讀取所有適用的 `AGENTS.md`，搜尋任務相關 Spec、Plan、ADR；確認實際程式碼、設定、API、型別及測試，不能只憑文件推定已實作。
2. **Requirements／Spec**：理解使用者目的、界線、User Story、REQ、EARS、AC；依等級建立或更新 Spec；規格有歧義或與既有核准內容衝突時停止受影響部分，提出問題。
3. **Plan（技術設計）**：針對已確認需求調查現況、選擇方案、記錄契約與風險；架構重大選擇提 ADR；Spec 已核准不代表技術方案也已核准。
4. **Plan（任務拆解）**：建立 TASK、相依、執行順序、完成條件與 TEST 計畫；確保 REQ → AC → TASK → TEST 可追溯。
5. **人工核准**：按任務等級確認 Spec、Plan、ADR；未核准不能把草案當實作授權。只被要求規劃時停在規劃／核准階段。
6. **Implementation**：在核准範圍內逐 TASK 開發，每項完成後做適當檢查，記錄實際進度。重大偏離需說明差異並重新確認，不得擅自擴大範圍。
7. **Review 與 Verification**：分別檢查（a）需求／AC 符合性及（b）技術品質／回歸風險；記錄兩個面向的結果，不要求一定由兩位審查者執行。逐 TEST 保留執行證據與未驗證事項。
8. **交付與同步**：更新 Plan 執行／驗證、必要的 Spec／ADR 和索引；確認狀態、連結及 Git diff；摘要交付內容及未完成項。未經明確要求不得自行 Git Commit 或 Push。

## 10. 來源標記、查證與防止假通過

文件中的重要技術結論、團隊決策、專案現況與驗證結果應依據下列標記，不得將推論寫成事實：

| 標記 | 用途 | 必要證據 |
| --- | --- | --- |
| `【官方】` | 官方文件可確認的規格與能力 | 有效官方連結、必要時版本資訊 |
| `【實測】` | 實際在指定環境執行和驗證 | 環境、指令／重現步驟、執行日期、實際結果 |
| `【實測:專案名】` | 僅在特定專案實測的結果 | 指定專案與相同實測證據；不可任意外推 |
| `【推論】` | 尚未驗證的合理判斷 | 明確寫出假設、不確定性及待驗證條件 |
| `【團隊】` | 已確認的團隊規則或決策 | 可追溯的 Spec、ADR、核准或會議紀錄 |

1. **每個正式章節開頭**寫一行精簡來源標記約定，例如 `> 來源標記：約定【官方】附原始來源；【實測】附可重跑證據；【推論】待驗證；【團隊】附決策依據。`。若全章無實測，明寫「本章無【實測】條目；待具備〈條件〉後驗證」。不要求每句一般描述都加標記。
2. **判斷檔案／目錄是否存在**：先執行 `ls`、`rg --files` 或等效查證；需據此提出重要結論時，記錄查證指令與關鍵輸出，不能虛構路徑。
3. **判斷 API／套件行為**：先查實際專案版本、設定、程式碼及可執行測試；官方說明只可證明官方宣稱，不代表本專案已實現。
4. **防止假通過**：清單差集、輸出比較或腳本驗證之前，確認輸入集合成功產生且不是非預期空集合；不能把空輸出直接視為成功。
5. **沒實測就不能標 `【實測】` 或 `passed`**；測試沒跑記 `not_run`，有阻礙記 `blocked`，保留原因。
6. **引用有效性**：外部來源連結須指向對應原始資料；專案內文檔、標題、路徑、程式碼識別必須先確認存在。
7. 可重新生成的大量原始輸出、暫存報告不應無故加入版本庫；在 Plan 留下可重跑指令、條件與結果摘要即可。

## 11. 停止條件、變更同步及完成前檢查

**停止受影響工作並取得確認**：

- 需求或驗收條件不明，不能安全推定關鍵業務規則。
- 使用者要求、已核准 Spec、已接受 ADR、Plan 或實際程式碼彼此衝突，需要選擇變更方向。
- 需要修改已核准的實質需求、已接受的決策或作出未授權的重大架構選擇。
- 需要破壞性 Migration、大量更名／搬移／刪除、覆寫使用者變更或其他超出授權範圍的操作。
- 同類失敗連續兩次，應回報嘗試方法、錯誤與可能原因，不無限制重試。

**變更與交付檢查**：

1. 修改重要結論、路徑或名稱後，使用 `rg` 搜尋整個相關工作範圍，包含 Markdown、程式碼、`*.sh`、`*.json`、`*.yaml`、`*.yml` 等，逐一確認引用、章節標號、索引及硬編路徑。
2. 確認每份正式文件具有**相同 Metadata 欄位順序**及該類型**固定章節**，沒有空白章節、虛構檔案或未標示推論。
3. 檢查建立日期與 ID 一致、流水號無衝突、狀態符合生命週期、取代關係雙向一致、連結可達。
4. 檢查 `REQ → AC → TASK → TEST` 對照無遺漏，Task／Test 狀態和真實證據一致；無適用項目要說明原因。
5. 保留原定計畫及變更歷史，不將事後結果重寫成原定內容；只同步本次實際影響的正本文件與索引。
6. 檢查 Git diff 僅含授權變更，沒有覆寫現有未提交工作；不自動 Commit／Push。
7. 交付時簡述改動與影響、實際跑過的檢查、未執行的驗證、風險與待人員決策事項；不能將未驗證事項宣稱已完成。

> **規則維護**：本制度需要調整時，先提出受影響條款與既有文件的相容／遷移影響，取得使用者確認後再修改。不得因個別任務自行變更全域命名、Metadata、章節或核准規則。
