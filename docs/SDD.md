# SDD 文件管理與執行規範

本檔是 AI 代理的 SDD 制度正本，由 [AGENTS.md](../AGENTS.md) 採用。採 Spec-anchored SDD，使用繁體中文；產品內容留在對應工作文件。

| 任務 | 必讀章節；另讀任務相關正本 |
| --- | --- |
| 建立／修改 Spec 草案 | 1～6、10～11；Spec 模板 |
| 開發／Plan | 1～5、7、9～11；Plan 模板及相關 Spec |
| ADR | 1～5、8、10～11；ADR 模板及相關決策 |
| 制度維護或完整審查 | 全文及受影響模板 |

## 1. 文件分工與初步建置

- Spec 管預期行為與驗收；Plan 管 Design、Tasks 與執行結果；ADR 管長期決策，不另建 Design 文件。
- 每項資料只維護一份正本，其餘留摘要與相對連結；正式需求建立後，專案背景引用 Spec。
- 建檔依序：確認要求與授權 → 查來源／現況 → 複製對應模板、配置 ID → 填已知內容與待確認事項 → 建立追溯 → 同步索引 → 驗收。
- 制度建置不代寫產品規格；規格草案不適用開發判級，無須先有 Plan。未知列「待確認：問題／影響／確認來源」，關鍵問題未解則保持草案。

## 2. 目錄、命名與索引

```text
project/
├── AGENTS.md                       # 代理入口
├── conventions/                    # 已採用的工具規範
└── docs/
    ├── SDD.md                      # 制度正本
    ├── guides/project.md           # 專案背景與現況
    ├── templates/                  # spec.md、plan.md、adr.md
    ├── specs/YYYYMMDD-NNNN-topic.md
    ├── plans/YYYYMMDD-NNNN-topic.md
    └── adr/YYYYMMDD-NNNN-topic.md
```

| 內容 | 位置 |
| --- | --- |
| 專案背景 | `docs/guides/project.md` |
| 格式模板 | `docs/templates/spec.md`、`docs/templates/plan.md`、`docs/templates/adr.md` |
| 正式文件 | `docs/specs/`、`docs/plans/`、`docs/adr/` |
| 索引 | `docs/index.md`，首次正式建檔才建立 |

正式文件路徑為格式示例，按需建立，不代表已存在。

- 檔名 `YYYYMMDD-NNNN-english-kebab-case.md`；ID 為 `SPEC-YYYYMMDD-NNNN`、`PLAN-YYYYMMDD-NNNN` 或 `ADR-YYYYMMDD-NNNN`。日期用首次建檔本地日期；流水號按類型＋日期從 `0001` 遞增，至少四位。
- 新建前查目錄、索引與可用 Git 歷史；合併前排除衝突。ID／首次日期永久不變，同號不自動關聯，檔名不加版本／狀態。
- `docs/index.md` 僅收錄 ID、標題、相對連結、狀態及主要關聯。新增、改名、狀態更新時同步；沒有正式文件時不建立索引。
- 模板不分配正式 ID、不進索引；目錄可用 `.gitkeep`，不預建空白正式文件。完成或被取代文件留原位；舊檔遷移先列 ID／路徑與引用影響，經授權才執行。

## 3. Metadata 與關聯

三類均按模板保留相同 9 欄及順序：`id`、`title`、`project`、`status`、`created`、`updated`、`related_projects`、`related_specs`、`related_adrs`。不自行增減。

- 類型由 ID 前綴與目錄判定。主要專案未確認用 `root`，跨專案只保留一份正本，其他列 `related_projects`。
- 模板日期留空，正式文件填 `YYYY-MM-DD`；`created` 對應 ID 日期，實質修訂更新 `updated`。
- 關聯為現存 ID 陣列，無值 `[]`，不填自己；正文附相對連結。Plan 關聯及同類型雙向取代關係留正文，不加欄位。
- 核准記日期、範圍、來源及確切版本（快照、雜湊或可還原差異）；僅 ID／日期不足，無法定位就詢問。

## 4. 生命週期與核准

| 文件 | 主流程 | 其他狀態 |
| --- | --- | --- |
| Spec | `draft → approved → implemented` | `superseded` |
| Plan | `draft → approved → implementing → completed` | `cancelled` |
| ADR | `proposed → accepted` | `rejected`、`superseded` |

- `approved`／`accepted` 須明確人工確認；Spec 核准不等於 Plan 核准，也不自動授權實作、安裝、部署或 Git 操作。實際開發後才標 `implementing`。
- 已核准需求／計畫的實質變更先列待核准提案，保留原核准正文，確認後套用；已接受 ADR 改決策須新增 ADR 取代，不覆寫。
- Spec 全部適用 AC 通過且證據完整才 `implemented`；Plan 任務及執行／驗證記錄完整並交代未解項才 `completed`，不等於整份 Spec 完成。Commit／建置成功不等於驗收。
- 退回、重啟、拒絕、取消、取代均記原因、日期、狀態與確認來源。

## 5. 模板使用

- 格式正本為模板；固定章節與欄位不刪併改名，章內可擴充。替換佔位值，不適用寫原因；規則與模板須同步。
- 按來源順序整理，沿用確認用語與既有 ID，只改必要差異；不得為重現而覆寫正式文件。

## 6. Spec：完整設計規格

用 [Spec 模板](templates/spec.md)，初始 `draft`。完整填寫需求、情境、業務規則、非功能要求及驗收；頁面／介面設計依模板填寫。

需求用唯一 REQ，行為優先 EARS；AC 含前提、操作、預期與 REQ，矩陣全覆蓋。跨文件加文件 ID；不以假設代替產品決策。

## 7. Plan：技術設計、Tasks 與執行

用 [Plan 模板](templates/plan.md)，初始 `draft`。查現況後寫方案、取捨、影響與風險；重大長期決策引用 ADR。

- `TASK-01`：工作、REQ／AC、相依、完成條件、驗證、狀態 `pending`／`in_progress`／`done`／`blocked`。
- `TEST-01`：AC／TASK、環境、步驟／指令、預期；執行後附日期、結果、證據及未執行原因，狀態 `not_run`／`passed`／`failed`／`blocked`。
- 保留完整 `REQ → AC → TASK → TEST`（含一對多）；純技術 L2 無 Spec 時用已確認來源與驗收基準，不造 ID。原計畫與實際結果分開，記錄修訂、差異及交付。

## 8. ADR：長期決策

用 [ADR 模板](templates/adr.md)，初始 `proposed`。僅用於長期架構、跨模組契約、資料擁有權或重要技術選型；記錄替代方案及取捨，一般 UI 不強制建立。

## 9. 後續開發分級與流程

開工前聲明等級與理由，使用者可否決；依 L3 → L2 → L1 判斷，不以少量檔案繞過升級。純草案依第 1 節。

| 等級 | 條件 | 流程 |
| --- | --- | --- |
| L1 | ≤3 檔，無業務行為／規則／AC 變更、Migration、公開契約變更、跨模組或重大架構影響 | 查現況 → 實作 → 驗證；不強制新 Spec／Plan |
| L2 | 不符合 L1、未達 L3，含一般跨模組重構 | Plan 草案 → 核准 → 實作／驗證；業務需求變更先核准 Spec |
| L3 | 跨模組完整功能／垂直切片、完整重大功能、核心架構或重大業務流程 | Spec 草案 → 核准 → Plan（Design＋Tasks）草案 → 核准 → 必要 ADR 核准 → 實作 → 雙面向 Review → 驗收同步 |

- 業務需求／公開契約變更至少 L2；符合既有規格的修復不算需求變更。純技術 L2 可只處理 Plan，Plan Mode 不代替文件或核准。
- 僅專案已確認微服務時：跨服務一律 L3，`*.Contracts` 等公開型別至少 L2；不由名稱推定架構。
- 只規劃不實作；依核准 TASK 開發。Review 分別留需求符合性與品質／回歸結果，不強制兩人。

## 10. 來源與驗證可信度

結論逐條或來源欄標記；文件開頭引用本節一次，不逐章重述。

| 標記 | 依據 |
| --- | --- |
| `【官方】` | 原始官方連結，必要時版本 |
| `【實測】`／`【實測:專案名】` | 本次執行的環境、指令／步驟、日期、結果；不得外推 |
| `【團隊】` | 使用者明示要求、決策或缺失，附原始指示／確認紀錄；不代表已核准或實測 |
| `【推論】` | 代理延伸的假設／建議／風險，附不確定性及驗證條件 |

- 混合來源分別標記，明示缺失不標推論。未測不標實測／通過；未實測範圍於開頭統一聲明，局部差異就近註明。
- 路徑先查證並附命令／關鍵輸出，不存在須交代搜尋限制。API／行為依實際版本、設定與測試判斷；官方說明不等於專案已實現。
- 比對先確認輸入成功、範圍正確且非意外空集合，空輸出不等於通過。證據只存一處，其餘引用；可重現的大量輸出不入版控。

## 11. 停止條件與交付檢查

| 停止條件 | 動作 |
| --- | --- |
| 需求／驗收不明、指示／文件／實作衝突 | 停受影響部分，列差異、影響、選項，確認改哪份正本；仍可整理待確認草案 |
| 改核准需求／決策或未授權重大架構 | 提判準、選項、建議；確認前不建立依賴決策的骨架；專案限制引用已採用正本的路徑／章節 |
| 同類失敗連續兩次 | 停重試，報嘗試、錯誤、原因與待人員決定事項 |
| 破壞性操作或越權 | 說明範圍、影響、替代方案，獲明確授權再做 |

交付前檢查 Metadata／章節／日期／ID、核准範圍、關聯／索引／連結、需求追溯及真實證據；用 `rg` 搜受影響引用（含程式、JSON、YAML、腳本），檢查 diff 保留既有變更。UTF-8 回讀實檔確認中文、換行、表格及佔位值，排除亂碼與非預期字面 `\n`。回報改動、實際驗證與未解事項，不捏造完成。

重現驗收固定要求、來源版本、核准內容、日期／時區與 ID 起點，獨立產出至少兩份；格式、需求／AC、來源分類、未決事項、判級與授權結論須一致，措辭可不同。記錄差異與證據，失敗修正後再驗；未驗不稱通過，同代理重跑不稱跨代理驗收。制度變更先說明影響並獲授權。
